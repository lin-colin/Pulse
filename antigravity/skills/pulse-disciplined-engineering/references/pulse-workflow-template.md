# Pulse 工程工作记录

这是一份填写结构，不是照抄的长篇报告。每栏用项目符号写事实；未知就写“未知”和如何验证。小任务可压缩为一行，但不能省略目标、证据、验证和限制。

## 1. 需求记录

- **分类/授权：** 回答、诊断、改动、验证或外部动作；写明用户实际授权的范围。
- **目标：** 用户最终能观察到的结果，不写实现手段。
- **非目标：** 本次明确不改变的行为、模块或外部系统。
- **成功标准：** 可验证的条件，例如“缺失值显示 `—`，局部测试覆盖并通过”。
- **事实：** 可定位的代码、日志、测试输出、文档或用户已确认的决定。
- **假设：** 尚未证实但暂时用来规划的前提；标注验证方式。
- **未知：** 会改变方案、风险或验证结论的问题；标注谁能回答或需要什么证据。

简洁示例：目标“电池温度失败时不显示 0”；非目标“不调整颜色阈值”；成功标准“读取失败展示 `—` 且测试覆盖”。

## 2. 只读证据与影响分析

先记录最小可用证据，或只提出一个最关键的阻塞问题。

- **证据：** 命令/文件/日志 → 发现 → 它支持或否定什么。
- **受影响入口：** 调用者、数据源、模型、UI、测试、脚本。
- **语义与数据：** 单位、缺失值、错误状态、兼容性、持久化或权限影响。
- **技术风险：** 边界、并发、资源生命周期、性能、回滚面。
- **范围判断：** 为什么该文件集合是最小范围；发现额外工作时回到决策而非顺手加入。

若存在取舍，增加“方案 A/B（代价、风险、推荐）”和“用户决定”；未获得关键决定前不要改动。

## 3. 验证计划

从成功标准反推验证，先列预期会失败的测试/复现，再列通过条件。

| 梯度 | 要验证什么 | 命令或步骤 | 执行状态/风险 |
| --- | --- | --- | --- |
| 局部 | 直接行为与错误路径 | 具体测试或复现 | 执行 / 不适用 / 无法运行及理由 |
| 全套 | 受影响模块和回归 | 测试命令 | 同上 |
| typecheck | 警告视为错误 | 具体命令 | 同上 |
| build/lint | 可构建性和静态规则 | 具体命令 | 同上 |
| 实机 | 真实硬件、权限或 UI 语义 | 手工步骤 | 同上 |

不能运行不是通过：写明阻塞原因、替代证据和残留风险。

## 4. 两阶段审查清单

**需求符合性审查：** 每个目标、非目标与成功标准是否都有差异或验证证据？是否改了未批准范围？

**代码质量审查：**

- 边界、空值、溢出和单位正确吗？
- 并发、时序和线程/队列归属正确吗？
- 观察者、定时器、任务、文件和句柄会正确释放吗？
- 错误、取消、无权限与不可用路径诚实吗？
- Swift 逻辑是否有中文“为什么”注释？
- 测试真的能失败且断言真实行为吗，还是模拟/基线让它假通过？

审查发现问题就回到最小改动和对应验证，不要把问题埋进交付说明。

## 5. 最终交付

按固定顺序简洁填写，不要把计划写成已完成：

1. **结果：** 完成/未完成；改了哪些文件和行为。
2. **依据：** 最关键的事实、根因或已确认决定；区分推断。
3. **验证：** 每个实际运行的命令及结果；未运行项及原因。
4. **限制：** 没有实测、无法访问或无法确认的部分和风险。
5. **未做事项：** 非目标、阻塞项和待用户决定项。
6. **范围/Git 状态：** 保留的用户改动、当前状态（或不是 Git 仓库），以及“未进行 Git 提交”。

## 6. 快速自检：禁止用一句话跳关

提交最终报告前逐项确认：

- 我是否把“用户认为的问题”与“已证实根因”区分开？
- 我是否在改动前建立了失败证据，或明确说明为什么不能建立？
- 我是否只改了已批准范围？
- 我是否真的运行了报告中写作“通过”的每条命令？
- 我是否把不能验证的项目、风险和未做事项写出来？

任意一项为“否”时，不得写“已完成”；回到对应关口补证据或如实报告未完成。
