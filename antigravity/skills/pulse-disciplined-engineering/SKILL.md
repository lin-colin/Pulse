# Pulse 受约束工程

**硬规则：禁止收到改动点就立即编码。** 每个请求必须依序经过：分类 → 复述目标/非目标/成功标准 → 事实/假设/未知项 → 只读证据或一个阻塞问题 → 影响分析 → 有取舍时方案与用户决策 → 失败证据/测试计划 → 最小改动 → 验证 → 需求符合性审查 → 代码质量审查 → 诚实交付。小任务可以把记录压缩成几行，但不得跳过关键关口。

使用 [工作记录模板](references/pulse-workflow-template.md) 保留可追溯的最短记录。这个技能管理工程方法，不重复产品领域知识。

## 先分类，决定授权边界

| 类别 | 可以做什么 | 不得做什么 |
| --- | --- | --- |
| 回答 | 基于已知信息解释、提出不确定性 | 写文件、改代码、运行会改变外部状态的命令 |
| 诊断 | 只读搜索、查看日志、复现、分析根因 | 修复、改配置或写数据；除非用户随后明确授权改动 |
| 改动 | 按下列关口实施最小修复或特性 | 扩大为重构、顺带优化或未授权外部动作 |
| 验证 | 运行适当的只读测试、构建和检查 | 把未运行的检查说成已通过 |
| 外部动作 | 仅在范围、目标和后果明确后执行 | 未授权的 Git 提交、数据库写入、发送消息、发布或破坏性操作 |

外部或破坏性动作（含删除/覆盖数据、Git 提交、数据库改写、发消息、发布）必须取得明确授权。只读数据库连接只可查询，绝不尝试写入。

## 必经关口

按顺序完成。任一关失败时，停止在该关，报告缺什么、为什么关键、下一步最小需要什么；不要用猜测或代码绕过。

| 关口 | 输入 | 必须输出 | 不通过时动作 |
| --- | --- | --- | --- |
| 1. 分类 | 用户原话、当前授权 | 回答/诊断/改动/验证/外部动作及允许范围 | 范围不清时只问一个最能解除阻塞的问题 |
| 2. 目标契约 | 需求与上下文 | 目标、非目标、可观察的成功标准 | 缺少关键成功标准时暂停，请用户决定 |
| 3. 认识边界 | 代码、日志、文档、用户陈述 | 事实、假设、未知项，三者不能混写 | 关键未知项不得伪装为事实 |
| 4. 证据 | 只读仓库检查、日志、测试或一个问题 | 支持/反驳问题的证据，或一个阻塞问题 | 无数据源、权限或可复现路径时停止；说明风险 |
| 5. 影响分析 | 已证实的现状、变更目标 | 受影响的入口、数据/单位、状态、并发、UI、测试、兼容性与回滚面 | 影响无法界定时继续只读定位，不改动 |
| 6. 决策 | 影响与可行方案 | 无取舍时明确理由；有取舍时给 2–3 个方案、代价、推荐项和需要的用户决定 | 用户未选关键产品/风险取舍时停止 |
| 7. 失败证据与计划 | 成功标准、风险 | 预期先失败的证据或复现、局部到高风险验证计划及不可运行时的替代证据 | 不能证明失败模式或验证路径时，不开始实现 |
| 8. 最小改动 | 已批准方案与测试 | 仅为成功标准所需的文件和变更；新增/修改 Swift 逻辑附中文“为什么”注释 | 发现需要额外重构或范围漂移时退回影响/决策关 |
| 9. 验证 | 已改动内容、计划 | 实际命令、结果、警告、未执行项和风险 | 任一必需验证失败，诊断根因；不得宣称完成 |
| 10. 需求符合性审查 | 原始目标、非目标、成功标准、差异 | 逐项判定满足/不满足及证据 | 不满足则回到最小改动或明确交付未完成 |
| 11. 代码质量审查 | 最终差异、测试与运行输出 | 边界、单位、并发、资源生命周期、错误路径、范围漂移、测试假通过检查结论 | 发现问题则修复并重跑受影响验证 |
| 12. 诚实交付 | 审查结论与实际输出 | 固定报告格式，不把推断写成事实 | 证据不足时明确限制和未完成事项 |

### 硬件与状态栏的额外前置条件

处理 Pulse 硬件指标、系统状态或菜单栏展示前，**必须同时读取本技能和** `antigravity/skills/pulse-hardware-monitoring/SKILL.md`。后者负责指标定义、数据源、单位、不可用语义与该领域必跑验证；本技能只约束决策、证据和交付方法。两者冲突时，停止并向用户说明冲突，不自行选择。

## 证据、方案与最小变更

- 先用只读命令定位真实入口、调用链和现有测试；不要只凭文件名或用户描述下结论。
- 诊断要输出“已证实原因 / 仍可能原因 / 排除项 / 下一条证据”，而不是把相关性写成根因。
- 有任何用户可见语义、数据源、兼容性、性能或风险取舍时，给出方案和推荐理由，等待用户决策。已被需求明确指定的选择无需重复征询，但要记录它。
- 失败证据优先是能先失败的测试或稳定复现；若不适用，说明为何，并用可复核的日志、断言或手工步骤替代。
- 改动只覆盖已批准成功标准。禁止广泛重构、顺带优化、改无关格式，或为“整洁”改变非目标行为。
- 不可用、读取失败或无权限时使用 `nil`、`—`、`不可用` 或明确错误路径；**不得用 `0` 伪装不可用**，不得以正常/绿色掩盖未知状态。
- 所有新增或修改的 Swift 逻辑都必须添加中文“为什么”注释，说明设计或保护的原因，不能只复述语句。

## 验证梯度

为每个梯度决定“执行 / 不适用 / 无法运行”，并记录理由和风险。按风险从低到高逐层升级：

1. 与改动直接相关的局部测试、复现或断言。
2. 受影响模块或全套测试。
3. warnings-as-errors 的 typecheck。
4. build 与 lint。
5. 必要时实机、真实权限、真实硬件或 UI 验证。

低风险文本改动不必伪装为跑过全套；跨模块、并发、硬件、状态栏、持久化或权限改动通常需要更高层级。任何无法运行的梯度都要写明原因、替代证据和残留风险。编译成功不是完成；没有符合成功标准的证据，也不得声称“已修好”。

## 两阶段审查

先做**需求符合性审查**，再做**代码质量审查**；不能合并成一句“看起来没问题”。

需求符合性审查逐项回查目标、非目标和成功标准，确认每项有可定位的差异或验证证据。代码质量审查至少检查：

- 边界值、缺失值、溢出与单位换算；
- 并发、线程/队列归属、时序与竞态；
- 文件、观察者、定时器、任务和句柄的资源生命周期；
- 错误、取消、降级与不可用路径；
- 是否产生范围漂移、未批准的重构或“顺带优化”；
- 测试是否因模拟过度、断言错误对象、未真正运行或错误基线而假通过。

## 借口识别：出现即回到前一关

下列说法不是例外，而是流程被绕过的信号：

| 借口或冲动 | 必须执行的纠正动作 |
| --- | --- |
| “这只是很小的改动，直接改就行。” | 写出至少一个可观察成功标准和一个失败证据，再判断最小验证。 |
| “我已经知道问题在哪。” | 用代码、日志、测试或系统读数确认；相关性不能替代根因。 |
| “编译通过，所以修好了。” | 回到验证梯度，运行能证明用户行为的测试或实机步骤。 |
| “没有测试环境，先改完再说。” | 不改；说明缺失验证、替代证据和风险，或请求所需环境。 |
| “顺手把附近代码整理一下。” | 从当前变更中移除；除非用户单独批准并完成新的影响分析。 |
| “读不到值先显示 0。” | 使用不可用状态；确认数据源、单位或权限后再显示数值。 |
| “用户应该就是这个意思。” | 仅在该假设不改变用户可见行为或风险时继续；否则提出一个阻塞问题。 |

## 微型示例：从请求到可信交付

用户说：“电池温度读不到时不要显示 0。”

1. 分类为**改动**；目标是失败时显示不可用，非目标是不调整温度阈值。
2. 只读定位温度数据源、格式化函数和 UI 调用方，确认当前 0 来自哪里。
3. 写失败测试：输入 `nil` 时当前输出为 `0` 或错误文案；成功标准是输出 `—`。
4. 只修改产生伪 0 的最小路径，加中文注释说明“防止缺失测点被误解为真实低温”。
5. 运行局部测试、受影响测试、typecheck/build；若没有实机传感器故障可复现，明确这项未实测及其风险。
6. 先回查“是否只改变失败展示”，再审查空值、单位和回退逻辑，最后如实交付。

## 停止条件与禁止项

出现下列任一情况即停止实现，带着证据向用户请求所需决策或授权：关键决策缺失；关键数据源或权限不能验证；验证失败；与用户现有改动冲突；需要 Git 提交、数据库写入、外部消息或破坏性动作但尚未授权。

绝不：把编译成功当完成、无证据称已修好、以 `0` 伪装不可用、进行广泛重构或顺带优化、Git 提交、数据库改写。不要覆盖、丢弃或悄悄合并用户现有改动。

## 固定最终报告

最终交付必须包含以下六项，内容只陈述实际完成和实际运行的结果：

1. **结果**：完成/未完成，以及改动的最小范围。
2. **依据**：关键事实、根因或决策的证据；明确哪些仍是推断。
3. **验证**：执行的命令、实际结果、未执行梯度和理由。
4. **限制**：未验证环境、数据/权限缺口和残留风险。
5. **未做事项**：刻意保留的非目标、被阻塞项和需要用户决定的事项。
6. **范围/Git 状态**：涉及文件、是否保留用户改动、当前 Git 状态（或“不是 Git 仓库/不可用”），并明确未进行 Git 提交。
