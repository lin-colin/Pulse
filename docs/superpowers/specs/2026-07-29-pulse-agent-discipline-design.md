# Pulse Agent Discipline Skill 设计规格

日期：2026-07-29  
状态：待用户审阅  
范围：为 Antigravity 提供高约束的软件工程行为技能；不修改 Pulse 产品代码。

## 目标

让 Antigravity 在 Pulse 项目中不再“收到改动点就立即改代码”，而是以可审计工程流程处理需求：理解、澄清、证据化诊断、方案选择、最小实现、测试、审查、验证和诚实交付。

## 架构：双层技能

### 1. `pulse-disciplined-engineering`

通用的高约束行为技能，适用于 Pulse 的任何代码任务。

它负责：

- 将输入分为咨询、诊断、改动、验证或任务管理；
- 禁止在需求不清、证据不足或风险未说明时立即改代码；
- 强制区分事实、假设、未知项和用户决策；
- 强制先追踪数据流与影响范围，再提出改动；
- 强制先建立失败证据，再进行最小实现；
- 强制运行与风险匹配的测试、typecheck、构建和实机验证；
- 强制自我审查并如实报告未验证项和限制；
- 禁止未经授权的 Git 提交、广泛重构、数据修改和“顺带优化”。

### 2. `pulse-hardware-monitoring`

保留已生成的项目知识技能。它负责硬件指标口径、数据源优先级、内存使用率/内存压力分离、UI 语义和验证命令。

当任务涉及系统功耗、电池温度、内存、CPU、状态栏颜色或活动监视器对照时，行为技能必须要求同时加载该知识技能。

## 处理流程

每个需求必须走以下关卡；未满足前一关，不得进入下一关。

1. **分类**：识别为回答、诊断、改动、验证或外部动作。
2. **理解**：以简短文字复述目标、非目标、成功标准；列出事实、假设和未知项。
3. **澄清或只读取证**：仅当未知项会改变实现或产生风险时，提出一个具体问题；否则通过只读代码、测试、日志或系统命令验证。
4. **影响分析**：写明数据流、受影响文件、调用方、测试和潜在回归。
5. **方案**：存在明显取舍时给出 2–3 个方案和推荐；获得必要的用户决策后才改动。
6. **测试设计**：为每个行为变化定义失败前可观察的证据和成功后的验收条件。
7. **最小实现**：只改已批准范围；新增逻辑包含解释“为什么”的中文注释。
8. **验证**：依次运行局部测试、全套测试、warnings-as-errors typecheck、构建、lint 和必要实机对照。
9. **双重审查**：先按需求检查完整性，再按工程质量检查正确性、边界、并发、错误处理和范围漂移。
10. **交付**：报告事实性结果、验证证据、未验证项、已知限制和未执行的外部动作。

## 强制停止条件

必须停止修改并向用户说明，而不是猜测或宣称完成：

- 缺少会影响行为、数据安全、UI 语义或发布方式的用户决策；
- 无法验证关键数据源、单位或权限；
- 测试、typecheck、构建或实机验证失败；
- 发现现有未相关改动且与本次范围冲突；
- 需要提交 Git、修改数据库、发送外部消息或执行破坏性操作，但用户未授权。

## Pulse 特定规则

- 不提交 Git。
- 不修改任何数据库数据。
- 代码新增或修改必须有中文“为什么”注释。
- 涉及硬件指标时，同时加载 `pulse-hardware-monitoring`。
- 状态栏、活动监视器和 AlDente 对照的结论必须标明是“已实测一致”“合理接近”还是“尚未实测”。

## 交付格式

改动任务的最终报告固定包含：

1. 结果：实际改了什么。
2. 依据：关键数据源、诊断证据或测试失败证据。
3. 验证：命令与实际输出摘要。
4. 风险/限制：未验证内容、私有接口或平台差异。
5. 范围：明确未改内容和是否未提交 Git。

- `antigravity/skills/pulse-disciplined-engineering/references/pulse-workflow-template.md`：可复制的需求分析、计划、审查和交付模板。

## 验收标准

- 技能前言明确禁止“立即编码”。
- 每个关卡有清晰输入、输出和停止条件。
- 流程同时适用于小修复和复杂诊断，不要求每次写冗长文档。
- 明确测试、审查和真实验证的区别，禁止“编译通过 = 已完成”。
- 两个技能职责不重叠：行为技能管方法，硬件技能管 Pulse 指标知识。
- 用户可把两份 Markdown 文件直接交给 Antigravity 使用。
